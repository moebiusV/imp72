# The C in `imp72`, and moving it to IMP

The rule (README, "What is next", item 2; decided 2026-10-28): all C is ported to IMP, and the seed (`stage0/` and its
tests, the trusted stage 0, which also stays what builds stage 1) may remain C. LLVM's ORC JIT is the only back end (the C back end
and pcc are gone), and the glue to the LLVM C API (`stage0/llvmorc.c`, `tools/ir2ll.c`), C today, is to move to IMP too. What
needs the operating system, the C library or LLVM is called from IMP through `CCALL` (`docs/FFI.md`).

This is the survey of what is C in `imp72` now (stage 2, `tools/direct.sh`), what each piece needs, and the order of the move.
`wc -l` counts; "seed too" marks code the seed (`imp72stage0`) also uses, which stays C there, so the IMP version is a second
implementation for `imp72` and the seed keeps its own.

## What the move needs

1. **A call through an address.** The semantic routine table holds the address of an IMP routine and `DOSEM` calls it with the
   parameters by reference (the tape patches the address into a `JSA`). IMP needs a way to call a routine given its address; `ffi.imc`
   can give it, as `CCALL` gave the call by value (the extension is the FFI's, not a change of IMP72's syntax).
2. **Doubles.** `CCALL` passes and returns a `long`. Where C needs a `double` (`strtod`) `sscanf` writes it through a pointer; the
   integer to double conversions of `pccirsem.c` are `FLT` and `FIX` of a `REAL` in IMP (the seed translates them now).
3. **Linker symbols.** The image uses the start and stop of section `impvars` and `dl_iterate_phdr`. From IMP these are `dlsym`
   (the program is linked `-rdynamic`) or a table of the variables the module writes itself (the tape has one for `/U`: the high segment).
4. **`main`.** A C program starts in `main`. **Done**: `lib/imp72main.imp` is a `SUBR MAIN(ARGC,ARGV)` that the C library calls with the values in registers; an IMP routine takes its arguments by reference, so `LOC(ARGC)` is argc (its low 32 bits: the rest of the register is not defined) and `LOC(ARGV)` is argv. It keeps them for `IMPARGC` and `IMPARGVP` and calls the main program, which is `impmain` (was `imp_main`: IMP has no underscore in a name, and the symbol is the port's own, not the tape's). It is a member of the library of its own, built by the seed with the rest of the runtime.
5. **The runtime library.** The seed's programs link `libimp72.a`, so the library is built before any IMP compiler exists. Making it
   IMP means building it with the seed. Decided: it is IMP, built by the seed (`tools/mklib.sh`, step 7).

## The order

1. `pccirsem.c`'s numeric helpers: **done** for `impstrtod` (`FCON` calls `SSCANF`), `diri2d` and `dird2i` (`FLOAT` and `FIX` of a constant use `FLT` and `FIX` on a `REAL`; a `REAL` passed as an argument is made an integer by `IFIX`, so the bits go through an integer with `MEMCPY`). `dirhigh` stays until `irstrval` moves (step 3).
2. `sys.c`: **done**, and the file is gone. The command line (`IMPARGV`, `IMPBYTE`), the listing and IR files (`IMPOPENLIST`, `IMPCLOSELIST`, `IMPOPENIR`; `fopen`, `perror`), `OUTSTR`/`OUTCHR` (`write` to the standard error), `INCHWL`, `RUNPGM`, the end of a fatal `ERROR` (the listing closed and `exit(1)`, where the tape goes to `FIN`; no `longjmp`) are in `src/impm.imp`, calling the C library with `CCALL`. The state the C that remains reads (`listing`, `quiet`) is IMP `COMMON` (`src/shared.txt`). What stays C: the arena's `mmap`/`mprotect` (`impcorebase`, `impcoreset`, `imp_core_info`, `imp_core_at`) and `impfclose` moved to the library (`lib/imp72rt.c`), because the flags of `mmap` differ by system and the tape's `FCLOSE` shadows the C library's in a `CCALL`; the library's default output has a setter, `impsetdefout`, that the driver calls with `LOC(LISTOUT)`; `stage0/impm_imp.c` has `impk_main`, `imp_error` and `imp_msg` for the C that is left, and goes with it.
3. The IR builders (`ir.c`) and the names (`IRSYMNAME` ...): **done**, in `src/pccir/ix.imp` (the seed keeps `ir.c`; `ir.o` is no longer linked into `imp72`). A node is eight words from `calloc`, kept on a list when freed; the text is written with `fputs`/`fputc` and a decimal writer that needs no 64-bit argument (the old halves of `IXICON` and `IXQUAD` are gone); the machines are a `DATA` table; `IRSYMNAME`'s cache is `COMMON` (`symc`, `nsymc`), cleared by `image.c` after an image is loaded. `pccirsem.c` is now the registration shims and `pcode`. The image skips the module `ix`'s variables (`stage0/image.c`). Two facts about IMP that cost time: a bracket address with a literal index, `[N+6]`, counts words (`[A+K]` and `[A+8*K]` count bytes and are scaled by what is written), and a call with fewer arguments than the routine has makes it dereference garbage (`IXPASS` is always called with five).
4. The table of semantic routines (`semtab.c`): **done**, and it is no longer linked into `imp72`. `DSEM` is the tape's routine again (`src/dir.imp`; the macro of `impsyn64.imc` that called a C `dsemi` is gone), with the table in C memory (two words a routine: the name's address and the routine's); the 'SEM' property is the id, 1 plus the place in the table, because an address does not fit it. `SEMCALL` (also `src/dir.imp`; `DOSEM` calls it where the tape jumps to the address in the `JSA`) calls the routine by `impsemcall` of the library, three lines of C that copy the five parameters and pass pointers to the copy (the routine may change them, and a semantic routine can call `DOSEM` again, so the copy is on the C stack). Not a facility of IMP72 itself: a call through an address is for the study of the FFI to decide (`CCALL` of a computed address). `SEMCOUNT`, `SEMNAME` and `SEMREMAP` are what `image.c` asks of the table. The seed's `IMP_SLOG` trace of semantic routines is not in the IMP one.
5. `image.c`: **done**, as `src/image.imp` (`IMPIMGSAVE`, `IMPIMGLOAD`; the module is in the lists of `tools/direct.sh`, `tools/pccir.sh` and `tests/direct/run.sh`). The file is words of 8 bytes and bytes, version 5. What the linker and the system give is in the library, `impvarlist` (the records of the section `impvars`, the writable part of the program from `dl_iterate_phdr`, each variable once, as three 64 bit words, so the record's size on the machine does not matter), `impcoreused`, `impcoreat` and `impptrsize`. `FSIZE` and `RELP` of the free module are `COMMON` now so that the image can name them.
6. The driver: **done**, `src/driver.imp` is the main program of `imp72` (the library's `main` calls `impmain`, which is `IMPD`): the options, the parts relative to the executable (`/proc/self/exe`, else `realpath` or the path), the temporary directory (removed by `atexit`, because a fatal `ERROR` exits), the kernel `IMPK` in the process with a command line built in C memory, and the back end: `llvmobj`, `llvmsave` and `llvmrun` of `llvmorc.c` (no underscores: they are called with `CCALL`), or `ir2c`/`cc1` and `cc` by `system`. Called by another name than `imp72` or `imp72stage...` (`imp72d`) it is the kernel alone, as the tests use it. The library keeps the command line (`impargc`, `impargvp`) and says the host's pcc target (`imphosttarget`). The seed's driver in `imp72s0.c` is only the seed's now, and `flavour0.c`, the `*_imp.c` wrappers and `pccirsem.c` are deleted: nothing in `imp72` called them. The image leaves the variables of the module `driver` alone.
7. The runtime library: **done** but for what only C can say. `lib/imp72io.imp` (PRINT, READ, FINI) and `lib/imp72rt.imp` (CALLI, BLT, IFIX, the shifts and rotation by a variable count, the byte pointers, EXECUTE) are IMP, compiled by the seed into one object (`tools/mklib.sh`; the seed's `IMP72CHARPTR=1` makes a byte pointer in a variable a pointer to characters in line, because the routines that do it for a general pointer are the ones being written). `lib/imp72sys.c` has the standard files, the call through a function pointer, the arena's `mmap`, the section bounds and the cells (`impca`) that carry a runtime call's arguments; `lib/imp72main.c` is `main`. To make it possible both code generators call the runtime as they call any IMP routine, by reference: the arguments of a call are stored in `impca` and their addresses passed, so the calls were renamed without underscores (`imppr`, `imprd`, `impblt`, `impcalli`, `implsh`, `impash`, `improt`, `impibp`, `impldb`, `impdpb`, `impxct`, `impblk`; data `impac`, `impxw`, `impbpp`, `impbpv`, `impca`), the back ends no longer treat `imp_*`, `ifix` or `fini` as C functions (they return words), and the runtime's own helpers are named `RTL...` so that they cannot meet a name of the compiler. No call takes a double, so the digits of a real are written by exact arithmetic on large integers (the same output as `printf` for 20000 random cases, which is what the ieee fuzz also checks). `ir2c`: a C back end in IMP was written and matched `tools/ir2c.c` byte for byte, then dropped with the C back end (it compiled out of
process, and LLVM is the only back end). What IMP taught: an array in IMP is the variable's own storage, so a block from `calloc` is addressed
`[P+(8*K)]`, not `P[K]`; `LOC(X)+1` is one word, not one byte; and a routine that calls itself keeps nothing in its variables across the call.

Each step: the build and `make check` pass before the next; the C it replaces is deleted from `imp72`'s link (and stays in the
seed where the seed uses it).
8a. The glue to LLVM's C API: **done**, as `src/llvm.imp` (the ORC JIT, the object file, `-S`; the seed keeps `stage0/llvmorc.c`). The calls are `CCALL`s of the C API's functions, which needed two things of the FFI and the build.
   *Names*: the symbol of a name was always lower case, and the C API's are `LLVMGetHostCPUName`; **a name with a lower case letter in it is now a foreign name exactly as written** (both code generators, `docs/FFI.md`;
   no IMP source had one), a name in capitals only is lower case as before. *The preprocessor*: what C chose with `#ifdef` is a module the build writes for the LLVM at hand, `tools/llvm.sh imp` (`llvmgen`):
   `LLVMNATIVEINIT` (the initialisation of the native target is an inline function of a header, so the target's own initialisers are called, named by the macros of `llvm-config.h`), `LVTSC` (how ORC takes a
   context: with `LLVMOrcCreateNewThreadSafeContextFromLLVMContext` or without), and `IMPLD`/`IMPLDHAVE` where there is no lld library. The enums of the C API are their numbers. The two things that C did
   with a function pointer and a memory stream are a call of the library's `IMPSEMCALL` (the entry of the JIT is called through an address) and files: `ir2ll` writes the text of the module to a file next to the IR
   (`IR.ll`), which LLVM reads, because `open_memstream` has an underscore. `imp72` needs the LLVM libraries now (the checks for a build without them are gone from the driver; the seed still has the stubs). What IMP taught:
   a C function returns an `int` in half a register, so the answers of the `LLVMBool` kind are masked to 32 bits; `fclose` of a `CCALL` in the compiler is the tape's `FCLOSE` (the library's `IMPFCLOSE` is the C one);
   `_` ends a name, so `open_memstream`, `dl_iterate_phdr` and the like cannot be named; a variable that no routine of a module uses is not made (`IMPCA` of the library needed `IMPCACLEAR`); and the symbol
   of a routine that the build does not rename is the plain one.
   Left: `lib/imp72sys.c` (the standard files, which are macros or variables of the system; the arena's `mmap`, whose flags differ; the section bounds, linker symbols with underscores; two calls through an address) and
   `lib/imphost.c` (`uname`, `dl_iterate_phdr`, `dladdr` and `readdir`, whose structures differ by system) say what only C can say; `impldhave`/`impld` are `stage0/impld.cpp`.
   `impfclose`, `impsetdefout` and the cells `impca` of `imp72sys.c` are IMP now (`lib/imp72io.imp`, `lib/imp72rt.imp`). `tests/native/*_main.c` are C by purpose (C calling IMP); whether they stay is for the user.
8b. The LLVM IR writer (`tools/ir2ll.c`): **done**, as `src/ir2ll.imp` (the entry `IR2LLRUN(IN,OUT,P32)`, the reading, the data and the functions) and `src/ir2llx.imp` (the expressions and the statements; two files because of the limit of
   2047 registers a compilation, see below), listed in `tools/direct.sh`, `tools/pccir.sh` and `tests/direct/run.sh`; `tools/ir2ll.c` is no longer linked into `imp72`, only into the seed. `src/llvm.imp` calls it, so there is no C shim. The output is the C's byte for byte: `tests/direct/ir2ll.sh` (in `make check`) gives the IR of the native tests, the oracle programs and the modules of the compiler, and the random IR of `tools/ir2ll-fuzz.py` (every operator, type, call shape and
   directive), to both writers, for pointers of 64 and of 32 bits, and compares what they write, errors included (checked once on 190 IR files and 600 random ones, and in the i386 container; the only difference is the message about a tree cut off
   by the end of the file, where the C prints what its stack had). Unlike the C, the state of a run is started again each time (the C keeps its sets of names from one run to the next). The text is built in buffers of its own, `open_memstream` having an underscore,
   and a number is written by a decimal writer that needs no 64 bit argument; the scanning of the numbers and words (`sscanf` and `strtoll` of the C) is done by hand, so that it is the same on a 32 bit host.
   What IMP taught here: **a compilation can name only 2047 registers** (`REGN` of `src/pccir/impsem.imp` is never given back and the index is 11 bits in the records), and past it the code is wrong without a word:
   a formal argument was read from a temporary that nothing set, in the last routine of a long file (`AREG1` says so now); an array of 262144 words (2^18) is silently one byte, so keep arrays below that;
   in `X AND Y => S` and `X OR Y => S` the `=>` takes only Y (`X AND (Y => S)`), so the whole condition is in parentheses: `((X) AND (Y)) => S`; labels are global to the compilation, not to the routine (a label twice is not an error and jumps to the wrong place);
   `(( A AND K)=K) =>` is called ambiguous; a routine that calls itself (the expressions here) pushes what it needs on a stack of its own and takes its arguments into variables at once.
9. The link: `src/driver.imp` links the executable with lld in the process (`LNK`: lld's driver through `CCALL IMPLD`, the files of the C library
   found by `TRYDIR` and `TRYDL`), for every system and architecture in its tables (Linux, FreeBSD, NetBSD, OpenBSD, macOS); a build without the lld library runs `ld.lld` as a program (`IMPRUNLD`), never `cc`. lld has no C
   interface, so `stage0/impld.cpp` (about 15 lines of C++, the one C++ file of the tree) gives its driver the plain C names `impld` and `impldhave`;
   `llvmorc.c` has stubs for a build without lld. The loader and the C library are found by what this program runs with (`lib/imphost.c`).
10. `tools/imprename.imp` (was `tools/imprename.c`): the part of `nm` and `objcopy` that `tools/direct.sh` used, in IMP, for ELF (32 and 64 bit, either byte order) and Mach-O, compiled by the driver that builds
    the stage in hand. Checked byte for byte against the C it replaced on the 22 modules. What IMP taught: `ELSE` after a chain of conditions is ambiguous, so the inner test is parenthesised; an empty string
    literal is not allowed; the main program comes before the `SUBR`s and the last `SUBR` has no semicolon; and a **bug of the code generator**: in `X[J-1]` the constant -8 of the address is encoded in 21 bits
    (`0x1ffff8` where `-8` is meant), so the program crashes; `K_J-1; X[K]` does not.
